# ADR 0001：热重启由插件自己的「脱离式辅助进程」完成

- 状态：**已接受**（`0.2.1-alpha.1-v1.1.0`）
- 相关：`docs/PLAN-hot-restart.md`、`docs/SPIKE-hot-restart.md`、`AGENTS.md` 第 3.8／3.9 节

## 背景

DSH **没有内置的重启能力**：`dsh` 启动器只负责把 profile 启动起来，退出走 `ctx.appExit(code)`（有界关停，5 秒兜底强退）。而本插件的 host 端模块**不会热加载**——改了 host 代码、`link:` 重装 bundle，都必须重启进程才生效（AGENTS.md 坑 ⑦）。于是「改完插件 → 重启 → 继续刚才的活」成了这个插件的开发者与使用者每天要走的路，而这条路上每一步都是手工的。

需求因此是两条：模型能主动请求重启并在重启后**自动继续**；用户能在设置页点一次按钮重启。两者必须共用同一套护栏与失败语义。

## 决策

**旧进程派生一个脱离式（`detached`）的一次性辅助进程，然后自己退出；辅助进程负责把新进程拉起来。**

```
旧进程：写 spec.json → spawn(detached, stdio:'ignore') 辅助进程 → 等本轮结束（工具路径）→ ctx.appExit(0)
辅助进程（活在旧进程之外）：等旧 pid 退出 → 等端口释放 → 按重放的启动规格 spawn 新进程
                          → 轮询 /api/agent-control/restart/status 等 bootId 变化 → 写 last.json → 退出
新进程：读 pending.json → 拉起会话 → 投递续作消息 → 删 pending
```

## 被否决的备选方案

| 方案 | 为什么不做 |
| --- | --- |
| 依赖启动器（DSHL / 桌面端）提供重启接口 | 计划明确不假设启动器有这种接口，也不去改它；插件要能在**任何**部署形态下工作，而不是只在某一个启动器下工作 |
| 只退出，让用户手动启动 | 那就没解决「模型自助重启并继续」这件事；且退出后如果没人拉起来，用户会以为实例挂了 |
| 进程内自替换（`exec` 语义） | Node 没有可移植的进程内 exec；Windows 上更没有。跨平台是硬要求（本插件同时要跑在 Windows 与 POSIX 上） |
| 先起新进程、再退旧进程 | 同一个端口不能有两个监听者：新进程会绑定失败。**必须先退、后起**，这也决定了必然有一段停机时间 |
| 起一个常驻的监督进程 | 引入第二个长期驻留的进程与它自己的生命周期问题（谁来监督监督者、怎么退出），收益不抵成本 |

## 后果

- **必须落盘交接文件**（`<DSH_HOME>/agent-control/restart/`）：新进程在旧进程死后才存在，除了磁盘没有别的通道。这是 AGENTS.md 3.8「插件不落任何数据文件」的**唯一受控例外**，边界写在那里。
- **辅助进程的 stdio 不能用管道**：它要活过父进程，而管道句柄会把两者绑在一起；本机沙箱下管道还会直接失败（AGENTS.local.md 第 2 节）。因此统一用文件描述符重定向到日志文件。
- **必须先让工具结果落盘再退出**：工具调用没有对应结果就进程死亡，会话日志尾部不合法（AGENTS.md 坑 ⑪）。所以工具路径是「返回结果 + `concludeTurn()`」之后，再由后台任务等 `whenIdle()` 与 `flush() === true` 双门，才真正退出。
- **停机时间由新进程启动耗时主导**（实测 6–10 秒，其中约 4 秒是 DSH 自身启动），不是由旧进程关停主导（实测 0.65 秒释放端口）。UI 文案与 `expectedDowntimeSeconds` 按这个量级给。
- **脱离式进程要能逃出父进程的作业对象**：本机实测 `detached: true` 在命令行拉起的实例上有效；由启动器（DSHL）拉起的实例上仍未验证，退路是 `CREATE_BREAKAWAY_FROM_JOB` 或 `cmd /c start`（见 SPIKE 的 S1）。
