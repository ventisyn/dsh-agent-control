## 5. 事故记录：墓碑缺 `id` 导致「每一轮都失败」

**现象**：`POST /turn/delete` 返回 **500**，错误 `format v4 system message id requires a string with content`；
同一轮对话本身也报 `本轮运行失败`。

**修复**：兜底用 `crypto.randomUUID()` 造 id；`buildTombstoneMessage()` 对两条路径都显式保证 id 是字符串；
新增 6 项回归测试，含强制走兜底的注入点 `buildTombstoneMessage({ create: null })`。

**已排除的更坏情况**：坏事件**没有**落盘（校验在写入前拒绝，日志里 0 条坏墓碑）。

## 6.1 事故记录：删一轮却把更早的轮次也从界面上藏掉

**现象**（用户报的）：三条问答里删**中间**那条（「第二句」），结果**第一条也从界面上消失了**。
数据层完全正确——真内核重放确认可见面恰好剩第一句与第三句——所以这是**界面层多藏了**。

**根因**：隐藏已删轮次时，从该轮的尾巴行往前逐个 `previousElementSibling`，
用 `cursor.querySelector('[data-chat-flow-kind="turn-tail"]') != null` 判断「是否到了上一轮」。
`cursor` 往上走到容器/分组时，其后代里当然有 `turn-tail`，于是循环一路吃到根部，
把该轮**之前的所有轮次**一起 `hidden`。兄弟遍历还默认了「所有行同层」这个没被保证过的前提。

**正确契约**（读 `dsh-client-ui-chat` 的 `ChatNodeSeat` 得到，不是猜的）：

```js
"data-chat-flow-kind": routedNode.kind,  // 含 'turn-tail'
"data-chat-turn": turn,                  // ← 每一行自己就标着属于哪一轮
"data-turn-tail": data.turn              // 只有该轮的尾巴行有
```

**修复**：改为在一个 `[data-chat-flow]` 容器里直接取 `[data-chat-turn="N"]`，
不再推断边界；并且**认不出归属时什么都不隐藏**（少藏只是界面滞后，多藏会让用户以为内容丢了）。
`syncTurnRows` 也挂到了 `window.__dshAgentControl`，便于控制台排障。

**真机复验**：✅ 用户确认「删除一轮后更早的轮次不再消失」。

**追加取证（2026-10-03 22:26，从会话日志反查）**：用户在一次连续测试里先后删掉 turn 2、3、4、5，
最后**单独补删 turn 1**。日志里留下了逐刀的墓碑写入时间，这一串时间戳不依赖人的记忆：

```
22:00:33 删 turn 2        22:20:00 删 turn 4
22:19:42 删 turn 3        22:26:31 删 turn 5
22:26:34 删 turn 1   ← 距 turn 5 只隔 4 秒，是紧接着补的一刀
```

而那条墓碑是 `surfaceOp = { op: 'replace', startSeq: 8, endSeq: 18 }`，
**精确只覆盖 turn 1**：`seq 7` 的 system prompt 与 `seq 20` 的 `turn/end` 都原样保留。

这一条同时排掉了两种相反的怀疑——既没有「删 turn 1 连带吃掉 system prompt」，
也没有「因为 bug 而藏不掉更早的轮次」。**6.1 的修复在数据层留下了可复核的痕迹，不再只靠人眼结论。**
可复核的方式就是下面的诊断器：

```
node test/log-inspect.mjs <会话 id>
```

## 6.5 墓碑日志的取证方式与「不是安全删除」的直接证据

轮次删除的正确性以前只能靠「界面上看着对」判断，这一节把它变成**可复核的数据**。
`test/log-inspect.mjs` 是只读诊断器：解压会话日志 → 解析事件 → 独立复刻一次 surface 代数 →
打印墓碑清单、逐轮「磁盘 vs 模型可见」对照、以及被遮蔽内容的原文预览。

对同一个会话的实测输出（turn 1~5 已被删净）：

  seq=  41  遮蔽 turn=3  区间 35..37   形状检查: ✅ 合规

「形状检查 ✅」逐条覆盖了三个真机踩过的坑：`id` 是非空**字符串**（坑 ⑧）、
`surfaceOp` 的键恰好是 `op/startSeq/endSeq`（坑 ① 的旧形状是 `start`/`end`）、

诊断器把原文直接打了出来（`user/message` 的「测试，回复这是第二句」、
`assistant/message` 的「这是第二句」……）。**模型看不到，但拿到这个日志文件就能还原。**
这正是 AGENTS.md 3.2 写明的那条限制，现在有了可复核的证据，而不是一句声明。

### 6.5.1 踩到的坑：会话日志是**多帧拼接**的 zstd，单帧解压只会看到会话头

```js
zstdDecompressSync(buf)   // ❌ 只解第一帧
```

第一帧只有 **253 字节**，内容是会话头那一行 JSON。而这个会话的真实内容是 **124 个帧**拼起来的
（`28 b5 2f fd` 魔数反复出现）。用单帧解压会得到「这个会话只有 1 行事件」，看起来像日志空了一样——
排查时极易被误导成「删除把日志清空了」。

正确处理有两种：

1. 按魔数手动切帧，逐帧解压后拼接（`test/log-inspect.mjs` 采用，坏帧单独计数，不让一个坏帧毁掉整次诊断）；
2. `createZstdDecompress()` 并把**整块 buffer 一次 `end()`**。

⚠️ 第 2 种写法**不能改成分多次 `write()`**：那样同样只会解出第一帧，而且不会报错。

### 6.5.2 活内核的交叉验证：`GET /turns` 给出了同一组答案

上面那张「逐轮对照」是**插件自己重算**出来的（复刻 surface 代数），严格说不是内核的答案。
补一个零推理的口径——直接问内核：

```
GET /api/agent-control/turns?sessionId=session-8c51d9be-28d2-410f-9645-586dada4830a
→ 200  {"ok":true,"sessionId":"session-8c51d9be-…","turns":[2,3,4,5,1]}
```

**与诊断器推算的 5 条遮蔽完全一致**（turn 1、2、3、4、5，一条不多一条不少），
而且是在这些删除发生**数轮之后**、会话仍在被追加的情况下查到的——说明墓碑是**持久事实**，
不是只在删除那一刻有效的一次性状态。

这一条同时把第 7 节里「模型看不到的证据链是插件自己算的」这个保留意见补上：
两条独立路径（插件复刻 / 内核 `turns`）目前给出一致答案。

## 6.2 事故记录：删掉了但界面不更新，要刷新才消失

**现象**（用户报的）：删除成功，**界面上那一轮还在**，手动刷新页面之后才正确消失。

**根因**：标记组件的 `useEffect` 依赖是 `[turn, sessionId]`，靠它自己**只在挂载时**拉一次
「已删轮次」。删除发生在这两个值之外——组件既不重跑，也没人通知它。
删除成功时弹窗只做了 `deletedTurnsCache.delete(sessionId)`，注释还写着「标记重新拉一次即可」，
但**没有任何东西会再去读那个缓存**。

**修复**：删除成功后广播 `dsh-agent-control:turns-changed`（带 `sessionId`），
标记监听它 → 清缓存 → 重新拉取 → 按最新结果隐藏。

**真机复验**：✅ 用户确认「删除对话确实在 UI 上实时更新了」。

## 6.3 事故记录：同步时「先恢复再隐藏」导致页面闪一下

**现象**（用户报的）：6.2 修好之后删除是实时的了，但**删掉后页面会闪一下**。

**根因**：每次同步都先 `restore()`（摘掉 `hidden`）再去拉数据、再隐藏。那一瞬间
已经藏好的行**重新显示了一帧**。

**修复**：把「恢复」和「隐藏」收进同一次遍历（`syncTurnRows`），只为「已不再被删的行」
恢复可见，其余保持原状——没有任何一帧会露出不该露的内容。

## 6.4 删除动效：收起折叠

用户先要求「像删除会话那样有个动效」，看过淡出版本后明确选了**收起折叠**。落地要点：

| 决策 | 为什么 |
| --- | --- |
| 过渡 `height` / `padding` / `margin`，不只是 `opacity` | CSS **无法对 `height: auto` 做过渡**，必须先 `getBoundingClientRect()` 量出像素高度；而且只压 `height` 会留下内边距与行距，收完还是一堆空隙、最后 `display: none` 时才「啪」地跳掉 |
| 逐行错开 50ms（`TURN_FADE_STAGGER_MS`） | 问题 / 回复 / 操作条三行同时收起会缩成一团；依次延后才是「自上而下卷起来」 |
| 严格分三帧 | ①本帧量高度、写过渡声明、让 `aria-hidden` 立刻生效（无障碍不延迟），**但不碰几何属性**；②下一帧写当前值作为起点；③再下一帧才压到 `0`。在设 `hidden` 的同一帧改几何属性的话，元素已经 `display: none`，浏览器根本不会跑过渡——**第一版就是这么写的，结果是「没有动画、直接消失」** |
| 收尾定时器可取消 | 被 `restoreAll` 恢复时清掉定时器，否则迟到的回调会把行又藏回去 |
| 量不到高度就放弃动画 | 宿主换 DOM 契约时不能让行卡在半折叠状态，直接 `display: none` |

尊重 `prefers-reduced-motion`；页面加载时就已删的轮次不播动画（否则每次进会话都在动）；
`MutationObserver` 触发的重复同步不重播动画。

**真机复验**：✅ 用户确认「可以了」（收起过程与时长都接受，无需再调）。
两个可调参数留在 `client.js` 顶部：`TURN_FADE_MS`（单行收起时长）与 `TURN_FADE_STAGGER_MS`（行间错开）。

## 8. 轮次删除改为「压缩同形事务」后的真机闭环 ✅

背景：旧墓碑（空 `system/message` 替换）在**运行时** append 合法，但 v4 **加载**校验要求
`system/message` 落在打开的轮次与步骤里，于是重启后会话打不开（AGENTS.md 坑 ⑪）。现在删一轮改为追加一笔
与内核手动压缩同形的独立事务：`compaction/start` → `compaction/summary` → `user/message`
（`compact-checkpoint` 替换）→ `compaction/end`，`turn: null`。

**用户操作**：新建测试会话 → 让模型依次输出「第一句 / 第二句 / 第三句」→ 删第 2 轮 → 追问模型
「还能在上下文里看到第二句吗」→ 再输出「第四句」→ **重启 `dsh web`** → 重新打开该会话、继续对话。

| 检查 | 结果 |
| --- | --- |
| 重启后打开会话 | ✅ 正常加载（旧写法此处即「历史加载失败」） |
| 重启后与模型对话 | ✅ 正常 |
| 模型自述 | ✅「那个位置原本有一轮对话，现在只剩一个占位说明……具体文字是什么，我的上下文里确实没有」；并指出「被删的是第二句」是从编号推出来的 |
| 日志里的删除事务 | ✅ 1 笔，`log-inspect` 事务检查「完整，落在轮次之间」；遮蔽 2 个节点（问题 + 回复），影子价格 54 |
| 被遮蔽的内容 | 仍在日志里（「测试，输出一句：第二句」与回复「第二句」）——**不是安全删除**，与设计一致 |
| 真实 v4 加载校验器（`test/v4-load-check.mjs`） | ✅ 当前日志 `OK`；对照组（在同一日志上补一条旧墓碑）`FAIL system/message does not match an open turn and step`；其余各轮模拟删除均 `OK`，第 2 轮被规划阶段判 `TURN_COMPACTED`（已删过、不在可见面上） |

**顺带修掉的诊断器 bug**（`test/log-inspect.mjs`）：

- 会话 id 只认一种拼写：磁盘目录是 `session-<uuid>` 时用裸 uuid 查会报「找不到会话」。现在两种都查。
- 可见面按**数值区间**折叠：replace 时把 `startSeq..endSeq` 之间所有 seq 都当成被遮蔽，于是把夹在中间的
  非 surface 事件（例如 `session-log-deepseek/delivery-accepted`）也列进「被遮蔽内容」，还漏算替换节点本身。
  现在与内核一致，按**节点位置**折叠。

**本节仍未验证**：`GET /turns` 跨重启的响应没单独抓；在已有内核压缩记录的会话里删轮次（`TURN_COMPACTED` 的真实样本）
仍未构造。

## 9. 投影缓存的历史遗留清理（2026-10-04）✅

AGENTS.md 3.3 记着「全盘扫描还找到 8 个早已删掉的会话留下的缓存记录」，但当时只推测是
「以前删会话时还没清缓存留下的」，**没有逐条核对**。这一节把它核完并清掉。

**核对方式（不依赖人的记忆，只用文件名与时间）**：

1. 收集 <code>$DSH_HOME/sessions/&lt;slug&gt;/&lt;id&gt;/</code> 下**所有**会话目录名（两种拼写各归一化去掉 `session-` 前缀）；
2. 列出 `storages/session_projcache/sessions/*.json`，按同一规则归一化后与上面求差集；
3. 用差的这一批的 **mtime** 与「清缓存的提交」的时间对照。

| 项 | 值 |
| --- | --- |
| 会话目录 | 61 个 |
| `session_projcache/sessions/*.json` | 69 个 |
| 差集（无对应会话的缓存） | **8 个**，与 AGENTS.md 记的数字一致 |
| 这 8 个的 mtime | 全部落在 **2026-10-03 12:38 ~ 16:37** |
| 清缓存那次提交的时间 | **2026-10-04 00:47**（`fix(session): delete a session without leaving cache or subagent residue`，已在当前 dev 分支上） |

**结论**：8 条的写入时间**全部早于**清缓存落地的时刻，所以它们是**修复之前**的历史遗留，
而不是「现在的清理逻辑没生效」。这也解释了为什么它们的会话目录早就不在了而缓存还在。

**处理**：删除这 8 个 json（只用文件名归一化匹配，逐个确认是普通文件、无符号链接、且不与任何现存会话撞名）。
删除后 `session_projcache` 从 69 → **61**，与 61 个会话目录**一一对应**，剩余孤儿 **0**。
删的是缓存文档，不涉及任何会话日志、工作区记账或附件。

⚠️ 这批文件在 `$DSH_HOME` 下、**不在任何会话工作区内**，所以本机的文件沙箱（`workspace-write`）
会以 `EPERM` 拒绝——这是预期的边界，不是文件权限损坏。删除需要一次更宽的权限；申请之前先复核了
「没有任何一个被半删」（8 个全在、文件数仍是 69）再动手。

## 10. 重启之后的 `GET /turns`（2026-10-04）⚠️ 结论比预期多一条

第 7 节留下的问题是「`GET /turns` 的答案跨重启是否仍然有效」。抓完发现，**有效性要分两半说**，
而且第一半是之前没记录过的行为：

| 时刻 | 会话 A（1 笔删除事务） | 会话 B（6 笔删除事务） |
| --- | --- | --- |
| 重启**前**（会话在内存里） | `200 {"turns":[2]}` | `200 {"turns":[3,4,5,6,7,9]}` |
| 重启**后**（该会话还没被打开） | `404 TARGET_NOT_FOUND` | `404 TARGET_NOT_FOUND` |
| 重启**后**（在界面上打开该会话） | `200 {"turns":[2]}` | `200 {"turns":[3,4,5,6,7,9]}` |

**两条结论**：

1. **答案是持久的**：打开会话后拿到的轮次列表与重启前**逐字一致**（`[2]` / `[3,4,5,6,7,9]`），
   说明删除事务确实落在日志里、重放后仍被识别。
2. **可读性依赖会话在本次进程里被打开过**：`handleListDeletedTurns` 走的是
   `findLiveSession(ctx.sessions.get(id))`——**只在内存里找活会话**。重启后没打开过的会话
   一律 404，与「没有删除记录」在错误码上无法区分。

⚠️ **源码注释与实际行为不一致，已改**：`src/index.mjs` 原来写着「墓碑是持久事实，因此这个答案在重启后
依然正确」——只对了后半句（答案是持久的），没写「必须先打开会话才能读到」。

**为什么这不是 bug**：`/turns` 读的是活动会话的事件流（`session.snapshotEvents()`），重启后未打开的会话
在内存里根本不存在，没有事件流可读；`404 TARGET_NOT_FOUND` 的文案也如实写了「只有活动会话的事件流可读」。
**但它有一个必须记住的后果**：界面上的「已删轮次」标记在重启后、会话被打开之前，拿到的是 404；
客户端把 404 当「没有已删轮次」并缓存。本轮实测中**没有**观察到已删轮次复活（见第 11 节），
因为标记挂载时该会话已经进入 store。

## 11. 界面侧：拒绝路径、就地刷新、DELETE_FAILED 的真实呈现（2026-10-04）

本轮把界面验证做成了**可复核的数据**，不再只靠「用户确认」：在页面里读 DOM / `performance` 条目，

### 11.1 重启后打开会话：已删轮次没有复活 ✅

### 11.5 删除后列表是否**就地刷新**：仍未观察到 ⚠️

这是本轮唯一没能闭环的一项，卡点是一个**产品约束**而不是测试偷懒：

- 侧栏（含「全部对话（显示已归档）」）只列出**工作区记账里存在的 5 个会话**，而这 5 个在本进程里
  **全部**被打开过 → 全部 `live` → 删除必被 `SESSION_LIVE` 拒绝，走不到「成功 → 刷新」那一步；
- 磁盘上那 57 个没打开过的会话（含大量一次性测试会话）在侧栏里**根本不可达**，UI 无法对它们发起删除。

**顺带把「切走就能删」彻底证伪了**（这条以前只在文档里写着，现在有实测）：重启后请用户从
「收到了确认测试」切到别的会话，随后复查 `/sessions`，它**仍然是 `live: true`**。
切走不释放、页面重载不释放（11.3 实测）——**只有重启进程**。

**要在下次重启时补的一步**（顺序很重要）：重启后**不要打开**目标会话，直接删它，然后核对
「行消失 + 页面没有重载」（判据见 11.6）。

### 11.7 `DELETE_FAILED` 的界面文案：仍未从真实失败渲染 ⚠️

本轮把它当正经实验做了一次，结果是**没能造出**这个失败：

- 在一个待删会话的目录里放一个用 `fs.openSync(file, 'r+')` **独占打开**的文件，再调删除接口 →
  宿主照样 `200` 删净了。原因：Node 在 Windows 上默认带**全部共享位**打开文件，所以宿主的
  `rm` 不会被挡住。**这条反过来说明「目录删不净」很难自然发生**（要真挡住得用
  `FILE_SHARE_NONE` 的原生句柄，那在 Node 里要额外手段）。
- 只读的投影缓存也不行：`removeProjectionCache` 把缓存失败收进 **warnings**、不抛错——
  这是**正确行为**（缓存没清掉不该让整次删除失败），已在 `src/session-delete.mjs` 里核实。

所以 `DELETE_FAILED` 这一支目前的证据链是**两段各自成立、接口未串起来**：

| 环节 | 证据 |
| --- | --- |
| 客户端把「错误码 → 文案 + 宿主原文」渲染出来 | 由**真实的 `SESSION_LIVE`** 走通（11.2） |
| `DELETE_FAILED` 的文案与「不得显示成任务正在运行」 | 客户端离线用例钉住（`test/client.test.mjs`） |
| host 在目录删不净时确实抛 `DELETE_FAILED` | 由离线用例覆盖（假文件系统让 remove 失败） |


- 已确认：`describeError` 会把「错误码对应的文案」与「宿主原始 message」拼在一起，且这条路径
  在 11.2 里被真实走通过（`SESSION_LIVE`）。
- 未确认：`DELETE_FAILED` 这一支没有从真实失败渲染过。本轮尝试过两条路，都不通：
  - **让目录删不净**（在目标会话目录里放一个被独占打开的文件）：目标会话在侧栏不可达（见 11.4），
    UI 发不出这个删除请求；
  - **只读的投影缓存**：`removeProjectionCache` 把缓存失败**收进 warnings**、不抛错，因此不产生 `DELETE_FAILED`（这一条本身是正确行为——缓存没清掉不该让整个删除失败）。
- 已有的替代证据：客户端离线用例把「500 + `code: DELETE_FAILED` + 宿主原文」这条链钉住，断言文案里
  **不得**出现「任务正在运行」（`test/client.test.mjs`）。

## 12. `TURN_COMPACTED` 的真实样本（2026-10-04）✅

第 7 节与第 8 节都留了这一项：「在已有内核压缩记录的会话里删轮次」应当被拒并判 `TURN_COMPACTED`，
但一直没构造出真实样本。这一轮造出来了，**全程走界面**。

### 12.1 怎么造的

1. 新建会话，依次发 4 条消息（每条都只让模型回四个字），确认界面里有 turn 1~4；
2. 在输入框敲 **`/compact`** —— 这是内核自带的手动压缩命令（`dsh-command-compact`），
   **不消耗模型轮次**；
3. 界面确认压缩真的发生了：命令结果写着「compact｜已压缩 10 条历史记录（约 1445 tokens）」；
4. 回到 **turn 1**，点它旁边的垃圾桶 → 勾选 → 确认删除。

### 12.2 界面上的答案（这就是要验的东西）

```
删除这一轮对话？
选中的这条回复 044dc15a-6c3e-41e9-97b0-ad275c446cae
将从模型的上下文中移除这一轮（问题、回复与该轮的工具记录），原位置只留下一句
「这里有一轮对话已被删除」的提示。会话本身、其它轮次与日志都保留——
被删内容仍留在日志与附件里，这不是彻底清除。

⚠ 这一轮已被压缩或不再连续，无法单独删除。（第 1 轮已经不在可见面上，无法单独删除）
```

两条都对：**「这一轮已被压缩或不再连续，无法单独删除。」是客户端给 `TURN_COMPACTED` 的文案**
（`client.js` 的 `error.TURN_COMPACTED`），括号里那句是宿主 `planTurnRemoval` 的原始 message。
又一次印证了那条失败语义：**码 → 文案、宿主原文 → 括号，两者都不吞**。

### 12.3 日志侧的证据

同一个会话的日志（`session-8321f3f3…`，58 个事件）里只有**一笔**压缩事务，而且**不是本插件写的**：

```
seq=53  compaction/summary  provider=deepseek-official
        shadowedRange = { start: 9, end: 45 }
        shadowedSeqs  = [9,10,11,12,19,27,29,36,38,45]
```

| 检查 | 结果 |
| --- | --- |
| 插件是否写了删除事务 | **没有**（`provider: dsh-agent-control` 零命中）——拒绝发生在第一个事件写入之前，符合 3.2 的「失败必须是拒绝，不是删一半」 |
| `GET /turns` 对它的回答 | `{"ok":true,"turns":[]}`——**内核压缩掉的轮次不算「本插件删除的轮次」**，与离线用例里那条显式断言（`deletedTurns` 只认自己的记录）完全一致 |
| `shadowedRange` 的字段名 | `{ start, end }`——**再次证实**不是 `surfaceOp` 那套 `startSeq/endSeq`（写离线样本时踩过，已修正） |

最后那条顺带说明：**界面在压缩后仍然显示 turn 1**（`data-chat-turn="1"` 的 4 行都在，未隐藏）——
它只是不再属于模型上下文，插件不该把它报成「已删除轮次」，所以界面上它照常可见、点删除才被拒。
这是设计如此：**「被压缩掉」与「被用户删掉」是两件事**。
